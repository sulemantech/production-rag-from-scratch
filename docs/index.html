The journey

Seven moves, each one measured before it counted

Not every idea worked. The two that didn't are in here too — knowing when to revert a plausible-sounding fix is as much a part of the discipline as finding one that works.

01baseline set

Started at 80.0% overall — with Physics and Chemistry badly behind

Biology sat at 85.5%, but Physics (56.4%) and Chemistry (64.7%) were dragging the average down. First job: find out why, without assuming.

02root cause, not guesswork

Audited every failure against its actual retrieved context

Each wrong answer was traced back to what the model actually saw, and classified — retrieval miss, reasoning error, corpus gap, or a genuinely bad label in the eval set itself. Several bad labels were found and corrected before any pipeline change was trusted.

03tested, discarded

Query rewriting recovered 17% of hard failures — not enough

Rewriting terse exam questions into fuller search queries before retrieval helped a handful of cases, but added latency and a new failure mode for a marginal gain. Not worth keeping.

04checked, cleared

Suspected the reranker — direct inspection cleared it

Pulled the full candidate pool before and after reranking by hand. The reranker was picking about as well as it could from what it was given — it wasn't the bottleneck.

05verified, kept

Generation-model capacity was the single biggest lever

Swapping the generation model alone — no corpus changes at all — took Physics from 56.4% to 84.6% and the overall score to 89.8%. Verified on the full 332-question set, not a cherry-picked sample.

06reasoned, measured, reverted

A targeted Chemistry fix looked correct — and still made things worse

Extracted and annotated dense tabular chemistry data (electron configurations) that had been flattening into unreadable text. Fixed real bugs along the way. Measured net effect across three iterations: flat-to-negative every time — the added candidates diluted retrieval more than the better content helped. Fully reverted rather than left as a plausible-looking regression.

07diagnosed, open

What's left: retrieval ranking, not corpus content

Chemistry's remaining gap is a matching problem — the right facts often exist but don't surface for how these questions are phrased. The next real lever is retrieval-side (embedding model quality), not another content fix. Not yet tested to a clean conclusion.

discipline 01

Measure the noise floor first

Every comparison was re-run once on identical input before being trusted — temp=0, reproducible against itself, or it isn't a comparison yet.

discipline 02

Fix the source before the code

Weak PDF extraction was solved with better source documents and dedicated table extraction — not more cleanup regex against unrecoverable noise.

What was built

Seven pipeline stages, each measured in isolation

No stage was assumed to be working. Every one of these was independently broken, fixed, and re-measured at least once over the course of the build.

pdfplumber, per-page extraction

Under the hood

Three pipelines: build the index, answer the question, prove it works

Ingestion and querying run on different schedules and different constraints — indexing runs offline whenever the corpus changes; retrieval runs on every single request and has to stay fast. A third, equally real pipeline — evaluation — is what turned every claim on this page from a guess into a measurement.

Where this goes next

What changes between a working demo and a production system

The live demo proves the pipeline works end to end. Turning it into something an institution could actually depend on is mostly an operations problem, not an algorithm problem — this is the honest gap between "it works" and "it's a product." This table is the summary; the production engineering log has the real, measured work behind it — starting with a full latency breakdown, not just a stated target.

Concern Current (demo) Production target
Serving Single Streamlit instance FastAPI behind a load balancer, horizontally scaled
Vector store Local ChromaDB file, ~9k chunks Managed vector DB (Qdrant / Pinecone), durable and built for scale
Caching None — every question re-runs the full pipeline Redis cache for repeated and near-duplicate queries
Auth & limits Open, unauthenticated demo API keys, per-tenant rate limiting
Observability Manual eval runs, checked by hand Continuous accuracy monitoring, latency/cost dashboards, drift alerts
Corpus updates Manual re-ingestion scripts, run locally CI/CD: new source → auto clean/chunk/embed → shadow-test → promote
Content compliance Source material cleared for academic, research, and commercial reuse Attribution/versioning tracked per source as more textbooks are added
Feedback loop None User corrections feed back into the eval set and corpus over time
