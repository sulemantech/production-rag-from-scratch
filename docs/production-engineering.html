What changes between a working demo and a production system

The main case study proves the RAG pipeline itself works — 89.8% on a 332-question benchmark. This page tracks the separate, ongoing work of turning that pipeline into something an institution could actually depend on: knowing where the time goes, what happens under real load, and how failure gets caught before a student sees it. Same discipline as the accuracy work — every claim here is measured against the real pipeline, not stated as a plan.

Milestone A — Visibility

Latency profiling: no single stage dominates

Instrumented every pipeline stage with a reusable timer, then ran it against a real 5-question sample — first coarse (retrieval / rerank / generation), then with retrieval split into its three actual sub-operations. The coarse view alone would have been misleading.

Instrumentation check: 0.21 (semantic) + 0.27 (BM25) + <0.001 (fusion) ≈ 0.47 — matches the outer retrieval timer's own average almost exactly, confirming the sub-stage breakdown measures the same work the coarse timer sees.
finding 01

The "biggest stage" isn't stable across measurements

Across three separate runs, the ranking between retrieval and reranking flipped every time (1.05s vs 1.82s; 0.81s vs 0.53s; 0.47s vs 0.80s). Generation was consistently the smallest of the three. At this sample size, retrieval and reranking should be treated as comparably expensive — not "one is the bottleneck."

finding 02

Retrieval's volatility is entirely in semantic search

semantic_retrieve swung 11x (0.07s–0.74s) while bm25_retrieve stayed within 1.3x (0.24s–0.31s). Likely cause: BM25 rebuilds its index from data already in process memory every call, while semantic search reads ChromaDB's index from a disk-backed file — subject to OS file-cache state. Flagged for a dedicated follow-up test, not yet confirmed.

finding 03

Reranking's cost is structural, not a bug

A cross-encoder score is a property of the (query, chunk) pair — unlike chunk embeddings, which depend only on the chunk, it can't be precomputed. Its cost scales directly with how many candidates retrieval hands it (currently 20). A real, tunable lever for a future latency/accuracy tradeoff — not something to eliminate.

discipline

Same noise-floor rule as the accuracy work

The full write-up — including the exact numbers from all three measurement attempts — is in the engineering log. This is the same "don't trust a single measurement" discipline that caught a false-positive embedding model result earlier in the project.

What's next

Three more milestones, scoped but not yet measured

Listed here for transparency, not to overclaim progress — these are planned, not done. Each will get the same treatment as latency profiling: real instrumentation, real numbers, findings written up before moving on.

Milestone B — Resilience

Guardrails & failure analysis

  • Input/output validation on the free-text question box
  • Llama Guard (via Groq) for content moderation
  • A real failure taxonomy — retrieval-miss vs. generation-misread vs. ambiguous-question — replacing ad hoc notes
Milestone C — Efficiency

Cost & caching

  • Per-query token/cost logging from Groq's own usage data
  • Exact-match caching for the fixed quiz-bank questions, which repeat by design
  • A swappable cache interface so a hosted store can replace the local one without a rewrite
Milestone D — Operability

Monitoring & incremental updates

  • Structured per-query logging (latency, tokens, retrieved chunks)
  • Generalizing this session's metadata-only Chroma update into "add one new book" without a full re-embed
  • CI-driven evaluation on a benchmark subset, not just manual runs
